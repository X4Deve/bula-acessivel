# Mega prompt inicial — Bula Acessível

**Origem:** transcrição integral da primeira mensagem do histórico deste projeto no Lovable, enviada em 15 de novembro de 2026.

**Natureza deste arquivo:** texto original recuperado do histórico; não é uma reconstrução. O conteúdo abaixo foi preservado sem reescrita.

---

Crie um MVP FULL-STACK funcional no Lovable com o nome "Bula Acessível", em português brasileiro, design universal e acessibilidade rigorosa. NÃO fazer apenas landing page nem protótipo clicável com dados fake. Gere frontend, navegação, autenticação, banco e permissões com Lovable Cloud (stack nativa, Postgres/Supabase gerenciado). Público-alvo: especialmente usuários cegos ou com baixa visão, operando NVDA + Windows/Chrome, VoiceOver e leitores de tela móveis. Missão: acesso confiável e GRATUITO ao texto de bulas oficiais; monetização SOMENTE da organização de lembretes e check-ins opcionais.

PRINCÍPIO INEGOCIÁVEL: zero alucinação médica. Nunca gerar, completar ou inferir princípios ativos, composição, indicação, posologia, contraindicações ou efeitos adversos a partir de IA. A bula deve vir de fonte rastreável e verificada. Bula oficial da Anvisa: https://consultas.anvisa.gov.br/#/bulario/ ; referência de consulta https://www.gov.br/anvisa/pt-br/assuntos/medicamentos/bulas-e-rotulos/como-acessar-o-bulario-eletronico . NÃO assumir que a Anvisa fornece API pública oficial documentada; não usar endpoints privados, scraping frágil, violação de robots ou dados simulados exibidos como reais. Criar camada de adapter provider para pesquisa real, com catálogo estruturado de itens validados no banco. Caso não haja fonte externa configurada ou nenhum registro local, informar honestamente "Ainda não temos esta bula em texto acessível no aplicativo" e oferecer LINK OFICIAL ao Bulário, sem inventar conteúdo. Criar fluxo de curadoria administrativa para cadastrar o registro oficial, nome, fabricante, princípio ativo, concentração, apresentação, número registro se conhecido, link oficial, versão/data da bula, conteúdo integral de cada seção em texto obtido de documentação oficial, data de verificação, aprovado por e status de publicação. Possibilidade de importar/extrair texto de PDFs OFICIAIS para revisão humana antes da publicação, se viável; se não for viável, habilitar colagem manual de texto extraído, sem alegar automação pronta. Adapter opcional de API externa para futura integração via secrets (ex. MEDICAMENTOS_API_KEY com fornecedor de dados autorizado) e endpoints server-side, SEM hardcode de chaves. Nunca confiar que um link arbitrário é oficial: permitir apenas host oficial verificável para links rotulados 'Anvisa'. Exibir fonte e data de última conferência em todas as seções, e link à bula original. Exibir aviso de desatualização quando curadoria vencida, sem remover acesso ao link oficial.

TELAS E ROTAS:
1. Página inicial pública: proposta de valor, botão "Pesquisar medicamento", "Entrar", "Criar conta", demonstração do processo, identidade Bula Acessível. Consulta pública acessível sem cadastro; criar conta necessário para salvar histórico/perfil.
2. Cadastro acessível: nome, email, senha, confirmar senha, consentimento granular/aviso LGPD, link política privacidade e termos; validação de formulário anunciada por leitores de tela; verificação de email se suportada. Nunca salvar senhas na tabela profiles; auth nativo.
3. Entrar: email/senha, mensagem acessível de erro, lembrar sessão, recuperar senha e sair. Recuperação de senha funcional se serviço configurado.
4. /app dashboard protegido: saudação, campo principal pesquisar por nome/princípio ativo, resumo de medicamentos em uso ATUAL (somente os que usuário marcou como 'Estou tomando'), consultados recentemente (distintos de uso), salvos, categorias, status da assinatura, próximos lembretes APENAS premium ativo, acesso a notificações e links claros. Empty states com ações.
5. /buscar: formulário search com label visível, botão Buscar, feedback aria-live, indicador loading, sem alteração intrusiva de foco, resultados em lista acessível. Filtros por nome, princípio ativo, fabricante se dados disponíveis; cuidado com medicamentos homônimos, exibir concentração e apresentação; sem resultados mostram link oficial e explicação real da indisponibilidade. Evitar debounced pseudo-busca.
6. /medicamentos/:id/bula: detalhes acessíveis da BULA DO PACIENTE quando verificada, navegação por H2/H3, sumário âncoras, seções "Para que serve", "Como funciona" se texto existir, "Como usar" (apenas reprodução literal de bula, sem personalizar), "Quando não devo usar", "O que devo saber antes de usar", "Reações adversas", "Composição" e informações adicionais só quando existem no documento. Usar texto selecionável / headings e botões pular seções. "Ouvir com leitor de telas" via estrutura semântica, sem TTS custom dependente de permissões. Controles A-/A+ de fonte, contraste normal/alto e espaçamento; preservar preferências. Botões "Salvar na minha biblioteca" e separadamente "Marcar como estou tomando" com confirmação: buscar/salvar NÃO presume uso. Manter snapshot da bula consultada e apontar versão mais recente quando disponível; distinguir snapshot histórico de bula oficial atual.
7. /app/minha-biblioteca: lista de bulas salvas, data da consulta, status "Somente consultado", "Em uso", "Uso encerrado", marcação opcional, histórico, filtro, remover, abrir, categorias personalizadas e por grupos terapêuticos APENAS se verificados. Categorias pessoais como "Meus favoritos", "Uso contínuo" não implicam orientação clínica. Usuário organiza próprios dados.
8. /app/medicamentos/:id: detalhes de um registro pessoal, histórico, opção marcar como em uso, deixar de usar, abrir bula acessível, categorias, configurar lembretes premium.
9. /planos: comparativo Gratuito x Premium transparente, sem valores inventados (preço "A definir" ou variável de configuração). NUNCA bloquear acesso à bula com paywall. Solicitar assinatura por botão "Solicitar Premium" que cria pedido PENDENTE sem cobrar, mostra que NÃO houve pagamento.
10. /app/assinatura: meus pedidos, status pendente/aprovado/rejeitado, diferencia claramente APROVAÇÃO ADMINISTRATIVA de PAGAMENTO REAL. Não afirmar 'compra concluída' se não existe gateway; premium ativado via entitlement após aprovação manual somente para piloto ou teste, sem comprovante financeiro, sem cobrar cartão. Preparar arquitetura para Stripe futuro mas não fingir cobrança.
11. /app/lembretes premium: horários DEFINIDOS pelo próprio usuário a partir da prescrição que recebeu, timezone America/Sao_Paulo, dias/recorrência, período início/fim, pausa, canal disponível; NUNCA gerar agenda automática a partir da bula nem prescrever horários/doses. Pode oferecer horários sugeridos como UI? NÃO, não sugerir. Agendamento persistente no backend. Se apenas notificações internas estiverem disponíveis, avisar que não são alertas externos garantidos. Não simular email/push enviados. Se email via provedor real exigir segredo, deixar configuração explícita/estado pendente. A agenda pode ficar salva e mostrar ocorrências, disparos devem depender de serviço configurado e testado.
12. /app/acompanhamento premium: check-in opcional "Como você está se sentindo com o uso?" com respostas subjetivas "melhor", "igual", "pior", "prefiro não responder" e campo opcional; mostrar histórico e mensagem neutra "Se sintomas persistirem, piorarem ou surgirem reações, procure um profissional de saúde. Em caso de emergência procure atendimento imediato." NÃO concluir que remédio funciona ou falhou, nem recomendar interrupção, dose, troca, diagnóstico.
13. /app/configuracoes: preferências de acessibilidade, consentimentos, exportar/apagar dados pessoais e pedidos; jamais mostrar dados de outros usuários. Privacidade e termos com textos introdutórios ajustáveis, não afirmar conformidade jurídica certificada.
14. /admin: painel restrito a role 'admin' validada no BACKEND. Pedidos de Premium com status pendente/aprovado/rejeitado, data do pedido, nome/email mínimo necessário, aprovar/rejeitar com motivo e registro auditoria. Não permitir usuário tornar-se admin editando profile. Gerenciar fontes e catálogo, submeter/validar/publicar bulas (apenas após revisar), gerenciar preço futuro sem cobrar, visão agregada sem exposição desnecessária da saúde. Criar bootstrap de admin SEGURO que NÃO confia em email fixo, variáveis client-side, e não concede acesso automático ao primeiro cadastro. Preferir processo controlado pelo proprietário via operação de backend/DB com instruções.

BASE DADOS: auth.users nativo; profiles(uid pk, display_name, preferences, timestamps); app_roles(user_id, role) só service role/admin; medicine_catalog(id, registration_code nullable, brand_name, active_ingredient nullable, manufacturer nullable, strength nullable, formulation nullable, source_url, source_type, verified_at, status); leaflet_versions(id, medicine_id, version_label, source_url, source_checked_at, full_text, sections_json, verified_by, approved_at, status, created_at) com links verificáveis e conteúdo apenas confirmado; user_medications(id, user_id, medicine_id, leaflet_version_id, state consulted/saved/taking/stopped, first_accessed_at, started_at nullable, stopped_at nullable, snapshot if necessary); categories and user_medication_categories with owner; search_history with owner; subscription_requests(id, user_id, type, status pending/approved/rejected, admin_reviewed_by, timestamps, note), subscription_entitlements(user_id, tier free/premium, status, valid_until nullable, approved_request_id), reminder_schedules(id, user_id, user_medication_id, local_time, timezone, weekdays, start_date, end_date, active, delivery_channel), notification_events(id, user_id, reminder_id, due_at, status, sent_at/error), symptom_checkins(id, user_id, user_medication_id, mood, notes, created_at), audit_events privileged only. Adapte o desenho do banco se houver solução mais segura e simples. IDs UUID, constraints, FKs, índices e RLS ativado e testado para TODAS as tabelas pessoais. Catálogo e bulas publicadas read-only público; rascunhos só admins. Alterações de assinatura/role e aprovar bula somente server-side, nunca via client trusted. Não criar fake medicamentos, lorem ipsum clínico, nem fake pedidos como reais. Dados demo só em ambiente de demonstração claramente rotulados.

SEGURANÇA: LGPD: dados de medicamentos usados/check-in são dados sensíveis de saúde. Minimização, opt-in explícito para acompanhamento, política privacidade, consentimento e exclusão, transport TLS, sem expor dados em logs, criptografia da plataforma, secrets server-side, RLS 'auth.uid()=user_id', rotas admin protegidas no cliente E NO BANCO, validadores Zod, rate-limit busca/edge functions quando possível, tratar erros e configurar operações idempotentes de lembretes. Sem dados sensíveis em query params ou trackers/analytics. Incluir aviso: "Informações de bula não substituem orientação médica; siga a prescrição recebida" nas áreas médicas sem sobrecarregar leitor de telas.

ACESSIBILIDADE WCAG 2.2 AA como meta verificável, não proclamar certificação: HTML semântico, landmarks header/nav/main/footer, h1 único por página hierarquia headings, labels explícitos e descrições, skip-link "Pular para o conteúdo principal", idioma lang=pt-BR, teclado 100%, tab previsível, sem keyboard traps, foco visível 3:1, contraste texto 4.5:1, alvos >=24x24 preferir 44x44, aria-live em status e erros, aria-current para navegação, preferir buttons/links nativos, não usar card clicável não semântico, dialogs acessíveis com foco gerenciado/escape, formulários com erro associado aria-describedby; alertas não precisam foco forçado, responsivo e zoom 200-400% sem perda. Componentes shadcn/ui com acessibilidade revisada; icons sempre com rótulos quando acionáveis; não depender só de cor. Praticidade extrema com NVDA em Chrome usando H para títulos, D para regiões, Tab/Shift+Tab, Enter, Espaço. Testar caminhos teclado e critérios com axe quando possível. Preferências alto contraste, fonte maior e espaçamento salvas.

VISUAL: design universal profissional, confiável saúde; azul-petróleo #0F4C5C e azul #155EEF em ações, branco, superfícies neutras claras #F8FAFC, verde moderado apenas sucesso; textos cinza muito escuro #101828; NÃO usar cores sem contraste. Usar fonte Inter/system com rem, layout clean, cards arejados, navegação principal intuitiva, ícones lucide com labels, componentes Tailwind/shadcn. Dark mode opcional apenas se acessível. Sem imagens decorativas que dificultem navegação.

FUNCIONALIDADE VERDADEIRA:
- Auth e CRUD devem funcionar conectados ao banco, não somente localStorage.
- Para busca, priorizar catálogo curado verificado; implementar caminho de integração futura por edge function com interface tipada e tratamento de ausência de credenciais. Se possível integrar fonte publicamente documentada, faça com cautela, identifique claramente quando não for a própria Anvisa e exija validação contra link oficial. Não preencher com bulas inventadas.
- Mostrar estados loading, empty, erro, sem permissão, indisponibilidade.
- Pedidos de Premium funcionais, backoffice aprova e cria entitlement via backend seguro, UI Premium habilita somente após entitlement.
- Agendamento real precisa de execução backend e canal real. Se não puder completar, não mostrar alertas falsos nem fingir entrega; rotular como 'disponível após configuração do canal' e apontar integração pendente no projeto.
- App funcional com navegação completa, rotas de proteção e layout acessível.

ENTREGÁVEIS: construa o projeto end-to-end agora com estrutura clara de arquivos, componentes reutilizáveis, SQL/migrations RLS, seed somente de CONFIGURAÇÕES não clínicas, documentação README no repositório com decisões, necessidades de integração oficial, configuração admin, checklist de testes NVDA, cenário de segurança e limitações reais. Fazer auto-verificação de rotas e fluxos. Se faltar segredo/pagamento/fonte, expor bloqueio honestamente, não simular sucesso. Projeto deve estar pronto para iterarmos e ser usado como MVP piloto, não publicar em produção automaticamente.
